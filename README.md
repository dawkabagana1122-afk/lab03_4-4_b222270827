## Босго сонгохын өмнөх бодит хэмжилт

Зааварт сануулсны дагуу эхлээд `measure.js`-ээр (20 VU, 1 мин) бодит тоог хэмжсэн. Гаралт: [`results/baseline.txt`](results/baseline.txt).

| Endpoint | p90 | p95 | p99 | Error rate |

| `/report` | 379.7ms | 389.05ms | 399.1ms | 0% |

| Бүх checks | | | | 98.21% амжилттай (2749 / 2799) |

Ачаалал: 20 VU, итерац бүрт 3 хүсэлт + 1с sleep → **~15.2 итерац/с**, endpoint тус бүрд ~15 хүсэлт/с, нийт ~45.7 хүсэлт/с.

## Алхам 2: Чанарын сценариуд (6 хэсэгтэй формат)

### 1. Performance сценарио — `/cart/add`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч бараа сагсанд нэмэхэд систем хурдан хариулах ёстой. |
| **Системийн төлөв** | API хэвийн ажиллаж байна, сервер дөнгөж асаагүй (халсан), өөр ачаалал байхгүй. |
| **Орчны төлөв** | Хэвийн ачаалал: **20 зэрэгцээ хэрэглэгч (VU)**, `/cart/add` руу **~15 хүсэлт/с**, нийт API руу ~45 хүсэлт/с. Сүлжээ: localhost. |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /cart/add` хүсэлт илгээнэ. |
| **Шаардлагатай хариу** | Систем HTTP 200 болон `{ ok: true }` хариу буцаана. |
| **Хэмжүүр** | 1 минутын цонхонд хүсэлтийн **95% нь 10ms-ээс**, **99% нь 25ms-ээс** бага хугацаанд хариулна (p95 < 10ms, p99 < 25ms). |

### 2. Reliability сценарио — `/pay`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэвийн хэрэглэгчийн төлбөрийн үйлдэл ихэнх тохиолдолд амжилттай болох ёстой. |
| **Системийн төлөв** | API ажиллаж байна. Төлбөрийн gateway хааяа timeout өгдөг (серверт ~5% алдаа суулгасан). |
| **Орчны төлөв** | Хэвийн ачаалал: 20 VU, `/pay` руу ~15 хүсэлт/с. |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /pay` хүсэлтээр төлбөр төлнө. |
| **Шаардлагатай хариу** | Амжилттай бол HTTP 200 `{ paid: true }`. Амжилтгүй бол HTTP 500 буцааж, хэрэглэгчид алдааг ил мэдэгдэнэ (чимээгүй алдаа гаргахгүй). |
| **Хэмжүүр** | 1 минутын цонхонд төлбөрийн хүсэлт амжилтгүй болох магадлал **POFOD < 0.08** (error rate < 8%). |

### 3. Availability сценарио — серверийн гэнэтийн зогсолт

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Сервер гэнэт зогсоод дахин асахад систем хурдан сэргэж, нийт хүртээмж хангагдсан хэвээр байх ёстой. |
| **Системийн төлөв** | API хэвийн ажиллаж байна. Нэг instance, load balancer болон нөөц сервер байхгүй. |
| **Орчны төлөв** | 20 VU тогтмол ачаалал (`/cart/add`, `/report`, `/pay` бүгд), 2 минутын цонх. |
| **Гадаад өдөөлт** | **Эвдрэл (crash):** серверийн процесс гэнэт зогсоно (Ctrl+C / SIGINT). Оператор **10 секундийн** дараа дахин асаана. |
| **Шаардлагатай хариу** | Зогсолтын үед хүсэлтүүд шууд алдаа (connection refused) буцаана, гацахгүй. Сервер асмагц хүсэлтүүд ямар нэг гараар хийх үйлдэлгүйгээр дахин амжилттай болно. |
| **Хэмжүүр** | 2 минутын цонхонд нийт хүсэлтийн **≥ 90%** нь амжилттай (availability ≥ 90%). Сервер асаах командыг өгснөөс хойш **сэргэх хугацаа ≤ 15s** (эхний амжилттай хариу хүртэл). |

### 4. Нэмэлт сценарио — `/report` (Performance)

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Тайлан гаргах нь хүнд үйлдэл боловч хэрэглэгчийн тэвчээрийн хязгаараас хэтрэхгүй байх ёстой. |
| **Системийн төлөв** | API ажиллаж байна. Тайлан 20000 мөр боловсруулдаг (200–400ms). |
| **Орчны төлөв** | 20 VU, `/report` руу ~15 хүсэлт/с. |
| **Гадаад өдөөлт** | Хэрэглэгч `GET /report` хүсэлт илгээнэ. |
| **Шаардлагатай хариу** | HTTP 200, `{ rows: 20000 }`. |
| **Хэмжүүр** | 1 минутын цонхонд хүсэлтийн **95% нь 450ms-ээс** бага хугацаанд хариулна (p95 < 450ms). |

**"Сайн сценариогийн 5 шинж"-ээр шалгасан нь:**
- **Итгэмжтэй:** босго бүр бодит хэмжилт дээр үндэслэсэн.
- **Үнэ цэнэтэй:** сагс, төлбөр, тайлан гэсэн хэрэглэгчид чухал үйлдлүүдийг хамарсан.
- **Тодорхой:** endpoint, HTTP method, хариуны төрлийг заасан.
- **Нарийн:** ачаалал (VU, хүсэлт/с), цонх, хувь (p95/p99) тоогоор илэрхийлэгдсэн.
- **Ойлгомжтой:** хүснэгт бүр 6 хэсгийн бүтэцтэй.

## Алхам 3: SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | k6 threshold |
|---|---|---|---|---|
| Performance | `/cart/add` latency | **p95 < 10ms**, **p99 < 25ms** | 20 VU тогтмол, 1 мин | `http_req_duration{name:cart}`: `p(95)<10`, `p(99)<25` |
| Reliability | `/pay` error rate | **< 8%** | 20 VU, 1 мин | `http_req_failed{name:pay}`: `rate<0.08` |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | **> 90%** | 20 VU, 2 мин, 10с зогсолт орсон | `checks`: `rate>0.90` |
| Нэмэлт (Performance) | `/report` latency | **p95 < 450ms** | 20 VU, 1 мин | `http_req_duration{name:report}`: `p(95)<450` |

**Босго сонгосон үндэслэл:**
- **Performance (10ms / 25ms):** бодит p95 = 1.68ms, p99 = 3.59ms. Зааврын жишээ болох 200ms нь бодит утгаас ~120 дахин сул тул юу ч хэмжихгүй. Тиймээс p95-д ~6 дахин, p99-д ~7 дахин зай үлдээсэн. Ингэснээр санамсаргүй хэлбэлзэлд унахгүй ч кодын регресс (жишээ нь санамсаргүй sync I/O нэмэгдэх) гарвал барьж чадна.
- **Reliability (8%):** серверт 5% алдаа суулгасан. 1 минутад ~930 төлбөрийн хүсэлт байхад алдааны хувийн стандарт хазайлт нь √(0.05·0.95/930) ≈ 0.7% болно. Тэгэхээр 8% нь 5% + ~4σ буюу санамсаргүй хэлбэлзэлд FAIL болохгүй, харин алдаа бодитоор нэмэгдвэл барина.
- **Availability (90%):** нэг instance-тэй, нөөцгүй систем тул 2 минутад 10 секундийн гараар сэргээх зогсолтыг тэсвэрлэх ёстой гэж үзсэн. 10/120 = 8.3% нь 10%-ийн төсөвт багтана.
- **Report (450ms):** дизайнаар хамгийн удаан хариу нь 400ms (бодит max 401ms). 450ms нь үүн дээр сүлжээ болон event loop-д 50ms зай нэмсэн утга.

**Error budget (цагаар):** 2 минутын цонхонд 90% availability → 120s × (1 − 0.90) = **12 секундийн "эвдрэх эрх"**. Төлөвлөсөн 10 секундийн зогсолт цагаар бол энэ төсөвт багтана. Алхам 5-д үүнийг **хүсэлтээр** дахин тооцно.

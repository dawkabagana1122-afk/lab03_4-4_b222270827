## Алхам 2: Чанарын сценариуд (6 хэсэгтэй формат)

### 1. Performance сценарио — `/cart/add`

| Хэсэг | Агуулга |

| **Системийн төлөв** | API хэвийн ажиллаж байна, сервер дөнгөж асаагүй (халсан), өөр ачаалал байхгүй. |
| **Орчны төлөв** | Хэвийн ачаалал: **20 зэрэгцээ хэрэглэгч (VU)**, `/cart/add` руу **~15 хүсэлт/с**, нийт API руу ~45 хүсэлт/с. Сүлжээ: localhost. |

| **Системийн төлөв** | API ажиллаж байна. Төлбөрийн gateway хааяа timeout өгдөг (серверт ~5% алдаа суулгасан). |
| **Орчны төлөв** | Хэвийн ачаалал: 20 VU, `/pay` руу ~15 хүсэлт/с. |

### 3. Availability сценарио — серверийн гэнэтийн зогсолт

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Сервер гэнэт зогсоод дахин асахад систем хурдан сэргэж, нийт хүртээмж хангагдсан хэвээр байх ёстой. |
| **Системийн төлөв** | API хэвийн ажиллаж байна. Нэг instance, load balancer болон нөөц сервер байхгүй. |
| **Орчны төлөв** | 20 VU тогтмол ачаалал (`/cart/add`, `/report`, `/pay` бүгд), 2 минутын цонх. |
| **Гадаад өдөөлт** | **Эвдрэл (crash):** серверийн процесс гэнэт зогсоно (Ctrl+C / SIGINT). Оператор **10 секундийн** дараа дахин асаана. |
| **Шаардлагатай хариу** | Зогсолтын үед хүсэлтүүд шууд алдаа (connection refused) буцаана, гацахгүй. Сервер асмагц хүсэлтүүд ямар нэг гараар хийх үйлдэлгүйгээр дахин амжилттай болно. |
| **Хэмжүүр** | 2 минутын цонхонд нийт хүсэлтийн **≥ 90%** нь амжилттай (availability ≥ 90%). Сервер асаах командыг өгснөөс хойш **сэргэх хугацаа ≤ 15s** (эхний амжилттай хариу хүртэл). |

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Тайлан гаргах нь хүнд үйлдэл боловч хэрэглэгчийн тэвчээрийн хязгаараас хэтрэхгүй байх ёстой. |
| **Системийн төлөв** | API ажиллаж байна. Тайлан 20000 мөр боловсруулдаг (200–400ms). |
| **Орчны төлөв** | 20 VU, `/report` руу ~15 хүсэлт/с. |
| **Гадаад өдөөлт** | Хэрэглэгч `GET /report` хүсэлт илгээнэ. |
| **Шаардлагатай хариу** | HTTP 200, `{ rows: 20000 }`. |
| **Хэмжүүр** | 1 минутын цонхонд хүсэлтийн **95% нь 450ms-ээс** бага хугацаанд хариулна (p95 < 450ms). |

**"Сайн сценариогийн 5 шинж"-ээр шалгасан нь:**
- **Итгэмжтэй:** босго бүр бодит хэмжилт дээр үндэслэсэн.
- **Үнэ цэнэтэй:** сагс, төлбөр, тайлан гэсэн хэрэглэгчид чухал үйлдлүүдийг хамарсан.
- **Тодорхой:** endpoint, HTTP method, хариуны төрлийг заасан.
- **Нарийн:** ачаалал (VU, хүсэлт/с), цонх, хувь (p95/p99) тоогоор илэрхийлэгдсэн.
- **Ойлгомжтой:** хүснэгт бүр 6 хэсгийн бүтэцтэй.

## Алхам 3: SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | k6 threshold |
|---|---|---|---|---|
| Performance | `/cart/add` latency | **p95 < 10ms**, **p99 < 25ms** | 20 VU тогтмол, 1 мин | `http_req_duration{name:cart}`: `p(95)<10`, `p(99)<25` |
| Reliability | `/pay` error rate | **< 8%** | 20 VU, 1 мин | `http_req_failed{name:pay}`: `rate<0.08` |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | **> 90%** | 20 VU, 2 мин, 10с зогсолт орсон | `checks`: `rate>0.90` |
| Нэмэлт (Performance) | `/report` latency | **p95 < 450ms** | 20 VU, 1 мин | `http_req_duration{name:report}`: `p(95)<450` |

**Босго сонгосон үндэслэл:**
- **Performance (10ms / 25ms):** бодит p95 = 1.68ms, p99 = 3.59ms. Зааврын жишээ болох 200ms нь бодит утгаас ~120 дахин сул тул юу ч хэмжихгүй. Тиймээс p95-д ~6 дахин, p99-д ~7 дахин зай үлдээсэн. Ингэснээр санамсаргүй хэлбэлзэлд унахгүй ч кодын регресс (жишээ нь санамсаргүй sync I/O нэмэгдэх) гарвал барьж чадна.
- **Reliability (8%):** серверт 5% алдаа суулгасан. 1 минутад ~930 төлбөрийн хүсэлт байхад алдааны хувийн стандарт хазайлт нь √(0.05·0.95/930) ≈ 0.7% болно. Тэгэхээр 8% нь 5% + ~4σ буюу санамсаргүй хэлбэлзэлд FAIL болохгүй, харин алдаа бодитоор нэмэгдвэл барина.
- **Availability (90%):** нэг instance-тэй, нөөцгүй систем тул 2 минутад 10 секундийн гараар сэргээх зогсолтыг тэсвэрлэх ёстой гэж үзсэн. 10/120 = 8.3% нь 10%-ийн төсөвт багтана.
- **Report (450ms):** дизайнаар хамгийн удаан хариу нь 400ms (бодит max 401ms). 450ms нь үүн дээр сүлжээ болон event loop-д 50ms зай нэмсэн утга.

**Error budget (цагаар):** 2 минутын цонхонд 90% availability → 120s × (1 − 0.90) = **12 секундийн "эвдрэх эрх"**. Төлөвлөсөн 10 секундийн зогсолт цагаар бол энэ төсөвт багтана. Алхам 5-д үүнийг **хүсэлтээр** дахин тооцно.

## Алхам 5: Мини chaos — серверийг 10 секунд зогсоох

`DURATION=2m k6 run slo-test.js` ажиллаж байх үед 40 дэх секундэд серверийн процесс руу **SIGINT** (Ctrl+C-тэй ижил дохио) илгээж зогсоосон. 10 секунд хүлээгээд `node server.js`-ээр дахин асаасан. Гаралт: [`results/chaos.txt`](results/chaos.txt). Цагийн бүртгэл: [`results/chaos-timeline.txt`](results/chaos-timeline.txt).

| Үйл явдал | Цаг |
|---|---|
| k6 эхэлсэн | 00:46:53.920 |
| Сервер зогссон (SIGINT) | 00:47:33.967 |
| Сервер дахин асаасан | 00:47:44.012 |
| Эхний амжилттай хариу | 00:47:44.111 |

- **Зогсолтын нийт хугацаа** (зогсоосноос эхний амжилттай хариу хүртэл): 44.111 − 33.967 = **10.144 секунд**.
- **Сэргэх хугацаа** (асаах командаас эхний амжилттай хариу хүртэл): 44.111 − 44.012 = **99ms**. Сценарийн "≤ 15s" шаардлага ✅ хангагдсан.

| Threshold | Бодит утга | Үр дүн |
|---|---|---|
| `checks` rate>0.90 (Availability) | rate=**87.67%** (4992 / 5694) | ❌ FAIL |
| `http_req_failed{name:pay}` rate<0.08 (Reliability) | rate=**15.75%** (299 / 1898) | ❌ FAIL |
| `http_req_duration{name:cart}` p(95)<10, p(99)<25 | p(95)=1.36ms, p(99)=2.22ms | ✅ |
| `http_req_duration{name:report}` p(95)<450 | p(95)=390.18ms | ✅ |

k6 нь `thresholds on metrics 'checks, http_req_failed{name:pay}' have been crossed` гэж бичээд exit code 99 буцаасан.

### Бодит availability — хүсэлтээр тооцсон нь

- **Availability = амжилттай / нийт = 4992 / 5694 = 87.67%.**
- **Хүсэлтээр тооцсон error budget:** 5694 × 10% ≈ **569 алдаа** зөвшөөрөгдөнө. Бодит алдаа **702** гарсан тул төсөв ~133 хүсэлтээр **хэтэрсэн**.
- **Цагаар тооцсон error budget:** 10.144s / 120s = 8.45% зогсолт → **91.5%** availability. 12 секундийн төсөвт **багтсан**.

**Хоёр тоо яагаад зөрж байна вэ?**
1. **Зогсолтын үед хүсэлт "хурдан" унадаг.** Сервер унасан үед хүсэлт connection refused-оор агшин зуур буцаж, `/report`-ын 200–400ms хүлээлт алга болдог. Итерац бүр ~1.3s байсан бол зөвхөн `sleep(1)` үлдэж 1s болдог (`iteration_duration` min=1s). `/cart/add`-д хэвийн үед алдаа гардаггүй тул түүний 200 алдаа нь зогсолтын итерацийн тоотой тэнцүү. Тэгэхээр 10.144 секундэд 200 итерац буюу **~19.7 итерац/с** болсон нь хэвийн үеийн 15.1 итерац/сээс (`pass.txt`: 45.40 хүсэлт/с ÷ 3) **~1.3 дахин** их. Зогсолтын нэг секунд хэвийн секундээс илүү олон хүсэлт "иддэг".
2. **`checks` нь `/pay`-ийн зориуд суулгасан 5% алдааг ч тоолдог.** Сервер огт унаагүй үед ч (`pass.txt`) нийт хүсэлтийн 1.58% нь алдаа байсан тул 10%-ийн төсвийн ~1.6%-ийг reliability-ийн алдаа эзэлж байна.

Тооцоо: зогсолтоор ~603 алдаа (cart 200 + report 203 + pay-ийн ~200) ба `/pay`-ийн хэвийн ~99 алдаа нийлээд 702 болно. Тэгэхээр зогсолт дангаараа 603 / 5694 ≈ 10.6% хувийг эзэлсэн. Энэ хурдаар (~59 алдаа/с) төсөвт багтах зогсолтын хугацаа нь ойролцоогоор (569 − 91) / 59 ≈ **8 секунд** байна.

**Дүгнэлт:** 10 секундийн гараар сэргээх зогсолтод 90%-ийн SLO нь **хэт өөдрөг** байсан. Учир нь цагаар тооцсон 12s төсөв нь хүсэлтээр тооцоход ~8s болж багасдаг. Сайжруулах хоёр арга бий: процессыг автоматаар дахин асаадаг болгох (pm2, systemd) эсвэл SLO-г ~85% болгож бодитой болгох.

**Reliability яагаад FAIL болсон бэ?** Сервер унасан үед `/pay` хүсэлт бүр унасан тул нэг эвдрэл хоёр SLO-г зэрэг зөрчсөн. **Тусгаарлах арга:** availability SLI-д зөвхөн серверт хүрч чадаагүй хүсэлтийг (`status === 0`, connection refused) тоолж, reliability SLI-д зөвхөн сервер хариу өгсөн хүсэлтүүдийн дундах 5xx алдааг тоолох хэрэгтэй. Ингэвэл нэг алдаа зөвхөн нэг SLO-д тоологдоно.

## Алхам 6: Threshold-оо зориуд эвдэх

[`slo-test-fail.js`](slo-test-fail.js) дээр `/report`-ын threshold-ийг `p(95)<100` болгосон. Харьцуулахын тулд `/cart/add`-ийнхыг `p(95)<50` болгосон. Гаралт: [`results/fail.txt`](results/fail.txt).

```
    http_req_duration{name:report}
    ✗ 'p(95)<100' p(95)=397.33ms
...
level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
exit: $?=0 (pipeline-ийн сүүлийн команд tee-ийнх), $pipestatus[1]=99 (k6-ийн жинхэнэ exit code)
```

- **FAIL-ийг харуулсан мөр:** `✗ 'p(95)<100' p(95)=397.33ms` ба `level=error msg="thresholds on metrics ... have been crossed"`.
- **k6-ийн exit code = 99.** CI pipeline 0-ээс ялгаатай кодыг хараад build-ийг зогсоодог.
- **Анхаарах зүйл:** зааврын `k6 run ... | tee results/fail.txt; echo $?` команд **0** хэвлэдэг, учир нь `$?` нь pipeline-ийн сүүлийн команд болох `tee`-ийн exit code юм. k6-ийн жинхэнэ кодыг zsh дээр `$pipestatus[1]`, bash дээр `${PIPESTATUS[0]}`-ээр авна. CI дээр `tee` ашиглах бол `set -o pipefail` тохируулахгүй бол threshold зөрчигдсөн ч build ногоон гарах аюултай.
- **`/cart/add` p(95)<50 яагаад PASS хэвээр вэ?** localhost дээр сүлжээ болон бодит ажил байхгүй тул p95 = 860µs байна. 50ms гэдэг нь ~58 дахин сул босго. Ийм босго "PASS" гарсан ч юу ч хэмжихгүй, зааврын 200ms жишээтэй адил асуудалтай. Тиймээс SLO-г заавал бодит хэмжилт дээр үндэслэх ёстой.

## Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү нь босгоны **тоог** зөв сонгох байсан. Зааврын жишээ болох `p(95)<200`-ийг шууд авсан бол бодит p95 нь 1.68ms тул тест хэзээ ч FAIL болохгүй, өөрөөр хэлбэл юу ч хэмжихгүй байх байсан. Тиймээс эхлээд `measure.js`-ээр бодит тоог хэмжиж, дараа нь хэлбэлзлийн зай (p95-ийн ~6 дахин, error rate-д ~4σ) нэмж босгоо тогтоосон. Хоёр дахь хэцүү зүйл нь сценарийн "хэмжүүр"-ийг k6-ийн хэмжиж чадах SLI-тэй тааруулах байсан: жишээ нь "сэргэх хугацаа ≤ 15s"-ийг k6 threshold-оор шалгах боломжгүй тул тусдаа цагийн бүртгэлээр (`chaos-timeline.txt`) хэмжсэн. Chaos туршилт availability сценарийн хэмжүүрийг **үгүйсгэсэн**: 10 секундийн зогсолт цагаар бол 12s төсөвт багтах ч хүсэлтээр тооцоход availability 87.67% болж 90%-ийн SLO-г зөрчсөн. Шалтгаан нь зогсолтын үед хүсэлтүүд агшин зуур унаж нэг секундэд ~1.3 дахин олон хүсэлт "идэгддэг", мөн `checks` нь `/pay`-ийн зориудын 5% алдааг ч тоолдогт байсан. Харин сэргэх хугацааны хэмжүүр (≤ 15s) бүрэн батлагдсан, учир нь сервер асаах командаас хойш 99ms-д хариулж эхэлсэн. Нэг серверийн зогсолт availability болон reliability хоёр SLO-г зэрэг FAIL болгосон нь SLI-г буруу тодорхойлбол нэг асуудал хоёр удаа тоологдож, аль SLO яагаад унасныг ялгахад хэцүү болдгийг харуулсан. Зориуд эвдсэн threshold нь exit code 99 буцааж CI-ийн quality gate хэрхэн ажилладгийг харуулсан бөгөөд `tee` ашиглахад `$?` нь 0 болж энэ кодыг нуудгийг олж мэдсэн. Хамгийн гол сургамж: SLO-г бодит хэмжилт болон хүсэлтийн тоогоор тооцох ёстой, цаг болон "сайхан" тоогоор тооцвол хэт өөдрөг болдог.
